## Exact wording and placement rules

1. Assign **one primary question and owner** to each URL. Put the natural phrase in a descriptive `<title>`, visible H1, opening answer and a relevant H2 when the section genuinely covers it. Add close variants where they improve clarity; do not target a word count, density, or a fixed number of repetitions. Google recommends distinct, concise titles and warns against stuffing and boilerplate ([title-link guidance](https://developers.google.com/search/docs/appearance/title-link)).
2. Open with a direct answer in the first short paragraph, then give the reader a route through the page. For an operations guide: definition → where it fits → steps → fictional case → skills → realistic next step. For an interview resource: question → reasoning → example answer → common error → practice prompt. Put a course CTA after the useful answer and at the end, where the next action is clear.
3. Use one prominent H1 for the page subject. H2s name major subquestions in a logical order; H3s belong inside an H2. On blog records, `post.title` is the H1, `post.seo.title` is the title tag, and `post.seo.description` is the meta description. The course and guide pages take their metadata from route/content records. The description should summarize the actual answer in plain language; Google may choose a different snippet ([snippet guidance](https://developers.google.com/search/docs/appearance/snippet)).
4. Give diagrams, case files and images descriptive names and alt text that explain the visual. Do not make decorative images repeat the target phrase. Label invented transactions, customer records and workflow examples as fictional. Quote current regulatory or credential facts only from dated primary sources.
5. Show truthful author/publisher, meaningful publication and revision dates, canonical URL and matching `BlogPosting`/breadcrumb data. The site's blog SEO generator already supports these fields. A date changes only after a substantive review, not after swapping keywords ([Google Article guidance](https://developers.google.com/search/docs/appearance/structured-data/article)).

## Internal linking map

Add **contextual, crawlable HTML links** in the relevant paragraph or section, with anchor text that describes the destination. Existing global related-link groups help discovery, but section-level links tell the reader why to follow them. Google explicitly recommends descriptive internal anchors and at least one link to every important page ([link guidance](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)).

| From | Link to | Example anchor and placement |
| --- | --- | --- |
| `/courses/` | `/career-guides/investment-banking-operations/` | “what investment banking operations analysts do” after the programme's operations-module explanation |

| Candidate trade-break case | Trade lifecycle guide and operations role guide | “see the full trade lifecycle”; “explore the operations analyst role” next to the case, with reciprocal links back to the case |

Do not force every link onto every page or reuse one exact anchor site-wide. Each approved new page needs a link from its hub, at least one relevant existing article/guide, and a reciprocal path to the next useful page. Update `src/seo/internalLinks.js` for route pages, blog JSON `link` blocks for contextual article links, and hub cards/navigation only when they help discovery.

The current route architecture includes large related-link groups on several pages. During implementation, inspect those rendered groups on mobile and keep the most useful nearby choices visible. Add the contextual links above in the body where their relevance is clear; a long list at the bottom does not replace a well-placed explanatory link.

Quality gate: run the project's build, lint, SEO checks and release QA, then inspect live rendered HTML and Search Console indexing after deployment. A local successful build does not prove Google indexed the page. For new topics, manually check the current India results before committing a URL. Google emphasizes original, helpful information and flags scaled low-value or city doorway pages ([people-first guidance](https://developers.google.com/search/docs/fundamentals/creating-helpful-content), [spam policies](https://developers.google.com/search/docs/essentials/spam-policies)).

For each released owner, also verify a 200 response, indexable robots rule, self-referencing canonical, sitemap inclusion, mobile readability, descriptive image text and a useful route from the blog/resource hub. Use the Search Console Core Web Vitals report to find real-user loading, responsiveness or layout problems before changing performance code ([Core Web Vitals guidance](https://developers.google.com/search/docs/appearance/core-web-vitals)). When an original worksheet or case is ready, share it with relevant educators or career communities through the site's normal outreach process and track only links that actually appear; do not treat outreach sends as earned authority.
